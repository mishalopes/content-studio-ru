# Производство серии

## Манифест

Хранить актуальные данные одной серии в JSON-массиве. Пример одной строки:

```json
{"id":"01","topic":"Тема","hook":"Вопрос на экране?","caption":"Согласованный полный ответ.","source":"inputs/clip.mp4","start":3.0,"duration":7.0,"output":"videos/01.mp4"}
```

Стабильные id соединяют тему, экранный текст, полный ответ и файл. Проверять id 01–50, заполненность текстов, точное соответствие последней согласованной таблице. Сохранять цвета, шрифты и размеры отдельно в конфигурации дизайна.

## Сборка

- Проверить фактическую доступность FFmpeg, Remotion и шрифтов до массового рендера. Переиспользовать существующий проект и зависимости; не пересоздавать всё без причины.
- Следовать установленным навыкам Remotion для регистрации, видео, шрифтов и детерминированной анимации. Можно рендерить прозрачную графику и объединять её с исходным видео через FFmpeg. У статичных текстов избегать дорогостоящего повторного рендера одинаковой графики каждого кадра.
- Для каждой темы подобрать уместный фрагмент. Сначала использовать разные планы и моменты, затем допустимые повторения; не обещать 50 уникальных съёмок из 4–10 коротких файлов. Не менять лицо или действия пользователя генерацией.
- Проверять метаданные поворота и фактическую ориентацию кадра. Кадрировать осознанно; не оставлять человека боком или с обрезанной головой при исправимом повороте.
- Сохранять исходные цвета. Подложка или градиент должны помогать чтению, не превращая видео в практически чёрный фон.
- При явном задании положения/размера текста сохранять их. Иначе учитывать интерфейс Reels: не размещать важный текст у нижнего и правого края; разумная отправная точка - поля 70–90 px слева, 140–170 px справа и минимум 280–320 px снизу при 1080×1920. Эти значения проверять на референсе и целевом интерфейсе, не выдавать за вечный стандарт платформы.
- Использовать короткие смысловые строки, без висящих предлогов. Не перекрывать лица и значимые действия. Проверять реальную ширину шрифта, а не только число букв.
- Хук должен быть виден сразу или за первые 0,3 секунды и оставаться читаемым до конца. «Читай описание» показывать без долгой задержки. Избегать резких мельканий и обязательного пословного появления длинного хука.
- Со звуком поступать по исходникам и брифу: оставлять пригодный исходный звук; не обрывать случайную реплику, которая меняет смысл. При отсутствии звука допустим немой ролик, но обозначить это. Не подменять выбранный звук без основания и не приписывать права на чужую музыку.
- Поддерживать обоснованную параллельность, вести логи. Успешный exit code сам по себе не доказывает пригодность MP4. Проверять файл ffprobe и полным декодированием; повторять только неудачные или изменённые номера.

## Контроль и выдача

Запускать проверку из каталога проекта:

```bash
python /path/to/skill/scripts/validate_batch.py --manifest batch.json --video-dir videos --expected 50 --full-decode
```

Проверка контролирует последовательность номеров, непустые поля, длительность 5–7 секунд с допуском контейнера, геометрию 1080×1920, кодек H.264 и полное декодирование. Если пользователь согласовал другой формат, передать соответствующие параметры ширины и высоты.

Дополнительно визуально просмотреть контактные листы ВСЕХ роликов и выборочные кадры по всей длине проблемных исходников. Сверить captions/NN.txt и экранные хуки с утверждённым источником; экспортировать полный ответ без сокращений. Счётчики, переносы и регистр не должны менять слова хука.

Архивировать videos/01.mp4–50.mp4, captions/01.txt–50.txt, редактируемую таблицу и общие описания. Проверить содержимое ZIP и число файлов. Сохранять по доступным правилам среды; давать реальные ссылки, не обещание выгрузки позже. Для больших серий удобно дополнить общий архив пятью частями по десять.
